# Scout Reliability — Implementation Plans

Generated by the `improve` skill on 2026-07-02 against commit `4ecf689` (branch `main`).
Focus: the user report that Scout **hangs** or **closes/exits unexpectedly** during normal
use, with poor failure UX. Method: an 11-dimension parallel code audit (90 agents) with
adversarial per-finding verification — **95 unique confirmed findings, 0 refuted**, which
collapse to ~30 root-cause clusters. Each plan below fixes one cluster.

> Advisor note: this supersedes nothing in `docs/RELIABILITY-ANALYSIS.md` (2026-06-25) — that
> document's 8 findings (P0-1..P2-2) were **re-confirmed still-present** by this audit and are
> folded into plans 004/005/006 with current line numbers.

## The one-paragraph diagnosis

Scout's engine was built for **one-shot CLI commands** ("sessions are per-command, no daemon"),
and almost every reliability defect is a place where that assumption meets reality and there is
**no deadline, no cleanup, or no crash guard**. Three families explain the user's symptoms:
(1) **Unbounded waits** on the startup path (an untimed PowerShell/WMI scan + synchronous
session reaping run on *every* invocation) and the teardown path (CDP `Browser.close`, launcher
`Kill`/`Cleanup`) — these are the "hangs." (2) **Panics with no recover** (send-on-closed-channel
races, CDP frame unmarshal via `utils.E`) and **process-wide teardown** (idle timer firing
mid-call, `os.Exit` in a plugin proxy, a watchdog that dies on its first panic) — these are the
"closes unexpectedly." (3) **Silent failure** (dead features that report success, raw `EOF`
errors, always-exit-1) — the "poor UX." The long-lived server surfaces (MCP, gRPC, agent, swarm)
each re-bolt a daemon onto the per-command engine and inherit all three families at once.

## Findings map (cluster → plan)

Each plan's "Why this matters" lists the exact finding IDs it closes. Summary:

- **001** ← startup WMI no-timeout; synchronous 3× reap ~11s/wedged-dir on every command.
- **002** ← `Browser.Close` CDP close before `Kill` (no deadline); `launcher.Cleanup` bare
  `<-l.exit`; `launcher.Kill` unconditional 1s `Sleep`; `New()` spawn→construct error paths leak Chrome.
- **003** ← `SessionHijacker.Stop`/`emit` send-on-closed panic; `mode_proxy` streamed-result
  send-on-closed panic; CDP `utils.E(json.Unmarshal)` panics with no recover in `consumeMessages`;
  reaper watchdog `recover()` that lets the goroutine die permanently; concurrent `Close` nil-deref.
- **004** ← `rodPage.Timeout(d)` is an **absolute** deadline stored as the page's permanent ctx →
  every page dies 30s after creation (REPL unusable, "context deadline exceeded" on everything).
- **005** ← idle-suicide (P0-1) + idle firing mid-call; `WithTimeout(0)` → bad selector hangs the
  server forever; no browser teardown on stdin-EOF; no liveness check on cached browser (P1-1);
  raw un-actionable tool errors; `open` tool leaks a headed browser.
- **006** ← reaper preserve-gate keyed on exe-name `scout` (kills embedders / renamed builds /
  daemons); PID-reuse preserves dead sessions; elevated-owner self-reap; torn `scout.pid` read.
- **007** ← `WaitFrameworkReady` JS is a SyntaxError (smart-wait is dead); `test-site` per-page
  `wait()` stalls ~30s; `WithCrawlConcurrent` no-op; `HealthCheck --timeout` no-op; console
  capture dead in `gather`; `NetworkRecorder.Stop` no-op; `SendWebSocketMessage`/`ws_connections`
  stubs; `swarm --depth` no-op.
- **008** ← exit code always 1; REPL dies silently on >64KB stdin; competing SIGINT handlers;
  `os.Exit` in plugin command proxy; `gather` swallows write failures; stale "background gRPC
  daemon" help text; `PersistentPreRunE` swallows flag-export failure (disables logging).

## Direction / architectural findings (for the maintainer to weigh — not bugs)

1. **The daemon/engine mismatch is now repeated five times.** MCP, `grpc/server`, `pkg/scout/agent`,
   `internal/engine/swarm`, and `pkg/scout/capture` each wrap a long-lived server around an engine
   whose sessions are per-command and whose reaper actively hunts "orphans." Every one re-derives
   idle timers, teardown, and session ownership, and each got them subtly wrong (see 005/006).
   Consider extracting a single **`ServerSession` ownership contract** (reusable session +
   heartbeat + explicit lifetime) that all five consume, instead of five ad-hoc lifecycles.
2. **Session ownership needs a positive token, not a negative "is it orphaned" scan.** The reaper
   infers ownership by probing PIDs and exe names; a start-token already exists for the *browser*
   PID (`BrowserStartToken`) but not the *scout owner* PID. Binding owner identity with a token
   (written at register, checked at reap) would collapse findings [38]/[64]/[65]/[78] into one fix.
3. **A pre-flight `scout doctor` / `scout browser ensure` step.** First-run Chrome download and the
   WMI scan both hide multi-second/indefinite latency behind the first real command. A visible
   pre-flight (download browser, warm the scan, report AV interference) would turn several "looks
   hung" reports into actionable output. Grounded in P1-3 and finding [4].

## Security findings (flagged; verify against main tree before acting)

These come from the long-lived-server dimension and several were read in a **stale git worktree**
(`.claude/worktrees/agent-a54a356f/…`); the code exists in the main tree (`grpc/server/`,
`pkg/scout/agent/`) but **line numbers must be re-confirmed on `main`** before a plan is written.
They are real-if-confirmed and high-severity, but they are opt-in server surfaces most CLI/MCP
users never start, so they are not in the critical-path plan set above.

- **Agent HTTP server unauthenticated by default + reflects any `Origin`** ([28]/[83]) — a visited
  web page could `fetch()` `localhost` and drive the browser. Verify `pkg/scout/agent/server.go`.
- **`scout server --insecure` exposes Eval/InjectJS to the whole network with reflection on** ([29]).
- **gRPC pairing auto-trusts any LAN device with no confirmation** ([63]) — verify `grpc/server/pairing.go`.
- **Plugin checksums (`VerifyChecksum`) are never enforced at load or auto-update** ([56]) — a
  tampered/MITM'd plugin binary runs with the user's privileges. This one is in the main tree
  (`pkg/scout/plugin/registry/`) and confirmed.
- **`0o600/0o700` are no-ops on Windows with no ACL fallback** ([86]) for cookie DBs / `vault.bin` /
  captures — protection rests entirely on inherited `%LOCALAPPDATA%` ACLs.

## Findings considered and rejected / deferred

- **gRPC/agent/swarm reliability findings ([64]/[84]/[85]/[89] partials)** — real in spirit but
  read in a stale worktree; deferred to a daemon-hardening pass that starts by re-confirming
  line numbers on `main`. Not rejected, just not yet plan-ready.
- **`RateLimiter` swallows `Wait` error with `WithRateLimit(0)`** ([88], PARTIAL) — the verifier
  found the claimed "0 disables pacing" mechanism is wrong (x/time/rate treats limit 0 as
  block-forever after burst), so the *stated* impact is inaccurate; the swallowed-error smell
  remains but is low-value. Folded as a one-line hardening note into 008, not its own plan.
- **`launcher` `processAlive` duplicates `session.ProcessAlive`'s documented Windows bug** ([94],
  LOW) — real duplication, but the practical Windows impact is a rare reusable-session stale-lock,
  already partly covered by 006. Left as a maintenance note in 006.

## How to verify a fix actually worked (project rule)

Per `docs/RELIABILITY-ANALYSIS.md` and the project's own guidance: **tests passing is not proof**
for these defects — they live at process/transport/timeout boundaries that unit tests stub. Each
plan's "Done criteria" therefore pairs `task test` with a **manual reproduction** on the real
Windows setup (e.g. suspend Chrome with a debugger and confirm `Close` returns within the deadline
instead of hanging).
